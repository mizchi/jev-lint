# The case against monorepos is really a case against slow tools

The monorepo debate goes around every couple of years, and every time it does, the same argument is made against the monorepo: it does not scale. Checkout is slow, CI is slow, the build graph is enormous, and every engineer is paying for changes they do not care about. I want to argue that this is not an argument about repositories at all. It is an argument about tools, and it dissolves the moment the tools are fixed.

Start with what a repository boundary actually is. It is a unit of atomic change and a unit of version history. That is all. Everything else people attribute to repository boundaries, such as ownership, access control, build isolation and release cadence, is a policy that happens to be easy to attach to a repository, not a property of one. You can attach ownership to a directory. You can attach a release cadence to a package. The repository boundary is doing that work only because it is the boundary you already have.

Now look at what the multi-repo setup costs. A change that touches an interface and its consumer becomes two changes in two repositories, ordered by hand, with a window between them in which the system is inconsistent. The consumer pins a version of the interface, and the pin is a promise that someone will eventually bump it, and that promise is broken in proportion to the number of consumers. Every organisation with more than a handful of repositories ends up with a dependency graph in which some edges are years stale, and no single person can say whether the system as a whole builds. That inconsistency is not an accident of the multi-repo setup. It is the setup.

The monorepo's answer is to make the atomic unit of change the whole system. A change to an interface and all of its consumers lands together or not at all. That is the property people want when they say they want a monorepo, and it is the property that multi-repo cannot offer at any price, because it is exactly the property that splitting the repository gives up.

So what does the monorepo give up in return? The usual list is checkout time, CI time and build time. Notice that every item on the list is a tool performance number. None of them is a property of atomic change. A version control system that can check out a subtree, a CI system that runs only what the change can affect, and a build system that understands the dependency graph would erase all three. Those tools exist. They are harder to set up than `git clone` and a shell script, and that difficulty is the true cost of the monorepo: not scale, but the requirement to adopt tools that understand the graph.

Here is the asymmetry that I think decides the question. The monorepo's costs are paid by tools, and tools improve. The multi-repo's costs are paid by people, in the form of coordination, stale pins and inconsistency, and people do not improve at coordination as the organisation grows; they get worse at it. One cost has a downward trend and the other has an upward one. A decision that favours the upward-trending cost because the downward-trending one is uncomfortable today is a decision that will look worse every year.

There is one honest argument for multiple repositories, and it is not about scale. It is that a repository boundary is a hard boundary, and sometimes you want a boundary that cannot be crossed by accident: a component that is open source when the rest is not, a system that must be auditable in isolation, a team that will be spun out. Those are reasons to split. "The build is slow" is not one of them, because the build is slow for a reason that has nothing to do with where the code lives.

If your monorepo is slow, the conclusion is not that monorepos do not scale. It is that you have a monorepo and multi-repo tools. Fix the tools.
