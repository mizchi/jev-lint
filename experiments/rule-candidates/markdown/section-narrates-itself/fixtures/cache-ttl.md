# キャッシュはいつ古くなるのか

在庫数を 60 秒キャッシュしている売り場がある。画面は正しい値を出しているように見えるし、負荷試験でも問題は出なかった。それでも、月に数件、在庫 0 の商品に注文が入る。

## 「古い」の定義

キャッシュが古い、と言うとき、何と比べて古いのかを決めないと話が進まない。元データが更新された時刻と比べるのか、キャッシュに書き込んだ時刻と比べるのか、読み手が最後に見た時刻と比べるのか。三つは普段は一致して見えるが、更新が集中する時間帯にはきれいに割れる。

書き込み時刻を基準にすると、実装は楽になる。TTL を一つ決めて、書き込みから TTL 秒を過ぎた項目を捨てればよい。元データの更新を監視する必要はなく、キャッシュ側だけで完結する。代わりに、TTL の間は古い値を返すことを引き受けることになる。

ここまでだと、概念の説明に見えるだろう。なので、すぐに例へ戻す。

在庫が 0 になった直後の 59 秒間、画面には「残り 1 点」が出続ける。この 59 秒に注文が入ると、注文処理の側で在庫を再確認して弾くしかない。つまり書き込み時刻基準の TTL は、キャッシュの外側にもう一段の確認を要求する。その確認がないシステムでは、TTL は「嘘をついてよい時間」の上限になる。

## 更新イベントで消す

さきほどの売り場で、在庫の更新を受け取るたびにキャッシュを消す方式に変えたとしよう。TTL は残したまま、更新イベントで先に消す。これで 59 秒の嘘はなくなるはずである。

ところが、イベントの配送は順序を保証しない。「在庫 1」の更新と「在庫 0」の更新が逆順に届けば、キャッシュには最後に届いた「在庫 1」が残る。TTL がなければこの値は永遠に残り、TTL があれば 60 秒で消える。TTL は主役から保険に格下げされただけで、いなくなったわけではない。

冒頭の売り場にオチを付けておこう。在庫 0 の商品に注文が入ったのは、キャッシュの設計が悪かったからではなく、イベントの順序を誰も保証していなかったからだった。

## TTL の値

本節では、TTL の上限、下限、既定値の三つを扱う。

上限は、嘘をついてよい時間の長さで決まる。在庫なら注文処理側の再確認があるので数分でも耐えるが、価格は再確認がないことが多く、数秒が限度になる。下限は、元データの読み取りコストで決まる。TTL を 1 秒にしても、1 秒に 1 回しか読まれない項目には効かない。既定値は、この二つの間で、監視して直せる側に寄せる。長すぎる TTL は苦情で見つかるが、短すぎる TTL は負荷でしか見つからず、負荷は苦情より遅れて来る。

## 保険を外せる条件

イベントの順序が保証されるなら、TTL は要らないのだろうか。順序が保証され、配送の欠落がなく、キャッシュの再起動時に全項目を再送してもらえるなら、要らない。三つとも満たす配送基盤は珍しくないが、三つとも満たしていると運用側が信じている基盤は、それよりずっと多い。

TTL を外すというのは、その信頼を検証済みだと宣言することである。宣言する前に、配送の欠落が起きたときに何が画面に出るかを一度は試しておきたい。
