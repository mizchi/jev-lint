# 型の絞り込みはどこで壊れるか

型の絞り込みを考えるうえで、判別共用体ほど適切な切り口もないはずだ。絞り込みが効く場面と効かない場面の境目が、判別共用体ではタグ一つの扱いに集約される。

## 判別共用体

`{ kind: "ok"; value: T } | { kind: "err"; error: E }` という型に対して、`if (r.kind === "ok")` と書けば、そのブロックの中で `r.value` が使える。コンパイラは `kind` の比較から、共用体のどちらの枝かを決めている。

要するに、この章の主題は型ではなく、値の形である。

絞り込みが効くのは、比較している式が同じ場所を指し続けているとコンパイラが確信できるときだけである。`r.kind` を比較したあとに `r` を関数に渡すと、その関数が `r` を書き換えたかもしれないので、絞り込みは解除される。実際には書き換えていなくても、解除される。コンパイラは関数の中を見ない。

## 効かない場面

ここでは、絞り込みが効かない三つの場面を順に述べる。

一つめは、コールバックの中である。`if (r.kind === "ok") { items.forEach(() => r.value) }` は通らない。コールバックがいつ呼ばれるかコンパイラにはわからず、呼ばれるまでに `r` が変わっているかもしれない。`const` で束縛した変数なら通るが、プロパティ経由では通らない。

二つめは、分割した条件である。`const isOk = r.kind === "ok"` と一度変数に入れると、古いコンパイラでは `if (isOk)` で絞り込まれない。新しいコンパイラは束縛を追跡するようになったが、追跡できる深さには限度がある。

三つめは、`in` 演算子と省略可能プロパティの組み合わせである。`"value" in r` は `value?: T` を持つ枝を除外しない。省略可能というのは「ないかもしれない」であって「ない」ではないから、これは正しい挙動で、そうであってほしくなかった、とは思う。

## 型ガード

では、型ガードを書けばよいのか。`function isOk(r): r is Ok` と宣言すれば、コンパイラは戻り値の真偽をそのまま絞り込みに使う。

使う、というのは、信じるということである。型ガードの本体が `r.kind === "ok"` を返していようが `true` を返していようが、コンパイラは戻り値の型宣言だけを見る。型ガードは絞り込みの穴を埋める道具であると同時に、絞り込みに嘘を混ぜる唯一の入口でもある。

その嘘を混ぜたのが半年前の自分でも、コンパイラは教えてくれない。型ガードの本体が宣言どおりのことを検査しているという保証は、誰が検査するのか。
