# 複合インデックスの列順

`WHERE tenant_id = ? AND created_at > ?` に対して `(created_at, tenant_id)` のインデックスを張った。実行計画は Index Scan を出しているのに、遅い。列順が逆なのだが、逆だと何が起きるのかを実行計画は教えてくれない。

## 列順

本節では、複合インデックスの列順、選択率、カバリングの三つを扱う。

複合インデックスは、先頭の列で並び、同じ値の中で次の列で並ぶ。`(created_at, tenant_id)` なら、まず作成日時で並び、同じ日時の中でテナントで並ぶ。`tenant_id = ?` で絞りたいとき、この並びは役に立たない。テナント 42 の行は、作成日時の全域に散らばっている。インデックスは範囲で読める形になっていて、その範囲が全域なのだから、テーブルを全部読むのと変わらない。

逆の `(tenant_id, created_at)` なら、テナント 42 の行は連続している。その中で作成日時の範囲を取れば、読む範囲は必要な行だけになる。等価条件の列を先に、範囲条件の列を後に。列順の原則はこれだけである。

## 選択率

列順を決めるのに選択率を見よ、と言われて、その選択率をどこで測ればよいのかがさっきから引っかかっている。

選択率は、条件で残る行の割合である。`tenant_id = 42` で全体の 1% が残るなら選択率は 0.01。等価条件が複数あるなら、選択率の低い列を先にする、と教科書には書いてある。ただしこの数字はテナントごとに違う。テナント 42 は 1% でも、最大のテナントは 40% を占めているかもしれない。最大のテナントで測った選択率で列順を決めると、残りのテナントでは最適でなくなる。

では、選択率を測る前に列順を決めてしまってよかったのだろうか。

ここまでで列順の話は見えた。次の問いはカバリングである。

## カバリング

テクニックの列挙はしない。

インデックスに含まれる列だけで問い合わせが完結するとき、テーブル本体を読まずに済む。これがカバリングである。`SELECT id, created_at FROM orders WHERE tenant_id = ?` に対して `(tenant_id, created_at, id)` があれば、テーブルへの往復がなくなる。

代わりにインデックスは太る。太ったインデックスは更新のたびに書き換えられ、書き込みの遅さとして現れる。読みの速さと書きの遅さは同じインデックスの両面で、どちらに寄せるかは、そのテーブルの読み書きの比率で決まる。比率は日によって変わるから、決めたら終わりではない。
