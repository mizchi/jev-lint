# 不安定なテストの正体

先に答えを半分だけ置く。不安定なテストの半分は、テストが悪いのではなく、テストが測っているものが不安定なのである。直したはずのテストが半年後にまた落ちる理由は残りの半分にあって、それは後で返す。

## 時間

`setTimeout` を 100 ミリ秒待ってから結果を確認するテストは、CI が混んでいる日に落ちる。100 ミリ秒は手元の機械では十分でも、共有ランナーでは足りないことがある。待ち時間を 500 に伸ばすと落ちなくなり、テストは 5 倍遅くなり、半年後にまた落ちる。

時間を待つのではなく、事象を待つ。結果が書き込まれるまでポーリングする、完了のコールバックを待つ、時計を偽物に差し替えて進める。三つのうち、時計の差し替えがいちばん速くて、いちばん多くのコードに手を入れる。

次は、順序に依存するテストを見る。

## 順序

白状すれば、順序依存はテストランナーの並列化で勝手に直ると思っていた。並列にすれば順序は毎回変わり、順序に依存するテストは毎回落ちるようになり、直さざるを得なくなる。直るに違いない。

ところが、並列化したあとに落ちたのは順序依存のテストではなく、共有のデータベースを使うテストだった。順序依存のテストは、ファイル単位で並列化されるランナーでは同じファイルの中の順序が保たれるので、そのまま通り続けた。並列化は順序依存を直さず、別の依存を掘り起こしただけだった。

順序依存を見つけるには、順序を明示的に乱すしかない。ランナーのシャッフルオプションを有効にして、落ちたテストが共有している状態を探す。グローバル変数、モジュールのキャッシュ、環境変数。見つかった状態を、テストごとに作って捨てるように直す。

## 測っているもの

テストが正しく書けていても、測っている対象そのものが不安定なら、テストは不安定になる。外部 API の応答時間、乱数を使う処理、スレッドの割り当て。

最後にもう一度だけ線を引く。

対象が不安定なら、不安定さをテストの外に出す。API は録画した応答に置き換え、乱数は種を固定し、スレッドの割り当ては結果が順序に依存しないことを検証する形に書き直す。置き換えられない不安定さは、テストではなく監視の仕事である。
