# ビルドキャッシュが当たらない朝

どうか、ここでの「ビルド」はコンパイルだけでなく、テストの実行とリントも含むと割り切って読んでほしい。キャッシュの話は、成果物が何であっても同じ形をしている。

## キーの決め方

キャッシュのキーは、入力の全部から作る。ソースファイル、依存のロックファイル、コンパイラのバージョン、環境変数のうちビルドが読むもの。どれか一つでも漏れると、入力が変わったのにキャッシュが当たり、古い成果物が出てくる。

漏れがないかを確かめる方法は、一つしかない。キャッシュを全部消して、同じコミットを二回ビルドし、成果物のハッシュを比べる。二回目がキャッシュから出てきて、一回目と同じなら、キーは入力を覆っている。うまくいっているに違いない。

ところが、この検査は「同じコミットで同じ結果」しか見ていない。違うコミットで同じキーになる漏れ、たとえばキーに含めていない環境変数がビルドに効いている場合は、二回ビルドしても見つからない。見つけるには、入力を一つずつ変えてキーが変わることを確かめる必要があり、それは入力の数だけ手間がかかる。

## 月曜の朝

月曜の朝、誰も何も変えていないのにキャッシュが全滅していたとしよう。「何も変えてないんですけど」と同僚が言う。ビルドは全部走り直しになり、CI は普段の四倍の時間がかかる。

金曜の夜に、CI のランナーのイメージが更新されていた。コンパイラのバージョンは同じで、ロックファイルも同じ。変わったのは、ランナーに入っている `libc` のバージョンだった。キーは `libc` を含んでいない。含めていれば、ランナーの更新で正しくキャッシュが無効になっていたはずで、つまり今回のキャッシュ全滅は、キーが正しかった場合に起きるべきことでもある。

含めていなかったのに全滅した理由は、別にあった。キャッシュの保存先が、ランナーのイメージごとに分かれていたのだった。

冒頭の月曜にオチを付けておこう。誰も何も変えていない、というのは正しかった。変えたのは基盤側で、変えたことをキーが知らず、保存先だけが知っていた。

## 残るもの

キーに何を含めるかは、キャッシュが当たらなかった朝に一つずつ増えていく。減ることはない。減らそうとして減らした項目は、次に当たらなかった朝に戻ってくる。

キーが十分かどうかを事前に証明する方法を、私は持っていない。持っている人がいるなら、その方法は入力の一覧を機械的に作る仕組みと同じもののはずで、それはビルドツールの仕事であって、キャッシュの仕事ではない。

足りない部分は、読者の手元のビルドで埋めてほしい。
