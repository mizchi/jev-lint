# 例外を握りつぶした日

この文章は、例外処理のベストプラクティス集ではない。

一つの `catch (e) {}` が本番で三ヶ月生き延び、その間に起きたことを追う。

## 握りつぶす

では、先に例外を握りつぶさずに落としておけばよかったのだろうか。

`catch (e) {}` が書かれたのは、外部 API の一時的な失敗でバッチ全体が止まるのを避けるためだった。一件の失敗で残りの九千件が処理されないのは困る、という判断は正しい。正しい判断が、失敗した一件をどこにも記録しない形で実装された。

三ヶ月のあいだに、外部 API の仕様が変わっていた。全件が失敗するようになり、全件が握りつぶされ、バッチは毎晩「成功」で終わった。話が長くなって恐縮だ。失敗に気づいたのは、下流の集計が三ヶ月ぶんずれていることに経理が気づいたときで、その時点でログには何も残っていなかった。

`catch (e) { log.warn(e) }` にしていれば、初日に千件の WARN が出ていた。出ていたとして、誰かが見たかどうかは別の問題である。

## 境界で変換する

例外を握りつぶすか投げ直すかの二択に見えるが、三つめがある。境界で、別の形に変換する。

バッチの一件ごとの処理は、成功か失敗かを戻り値で返す。失敗は例外ではなく値になり、バッチの本体は失敗の件数を数え、閾値を超えたらバッチ全体を失敗させる。一件の失敗で全体を止めない、という元の判断は保たれ、全件の失敗は初日に見える。

境界をどこに置くかで、変換の意味は変わる。一件ごとの処理の内側で変換すれば、その処理は例外を投げない関数になる。外側で変換すれば、例外を投げる関数を、投げない形で呼ぶ包みができる。これについては、次の節で詳しく見る。

## 境界の数

まず、境界の定義から。

境界とは、失敗の意味が変わる場所である。外部 API の呼び出しでは「接続できなかった」が失敗で、バッチの一件では「この行を処理できなかった」が失敗で、バッチ全体では「処理できなかった行が多すぎた」が失敗になる。三つの失敗は同じ例外から始まっていても、意味が違う。

意味が変わる場所ごとに変換を置くと、変換の数は境界の数と同じになる。境界を減らせば変換は減るが、減らした境界の内側では、失敗の意味が混ざる。混ざった意味を `catch (e) {}` で一括して捨てたのが、三ヶ月の始まりだった。
