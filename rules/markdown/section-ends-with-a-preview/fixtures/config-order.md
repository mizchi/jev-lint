# 設定はどこから読むべきか

環境変数、設定ファイル、コマンドライン引数、コードの既定値。四つの置き場所があって、同じキーが二つ以上に書かれたときにどれが勝つかを、動かしてみるまで誰も言えない。それがこの問いの中身である。

## 環境変数か、ファイルか

では、先に環境変数を読んでおけばよかったのだろうか。そうしたかった、とは思う。環境変数は起動時に確定していて、コンテナの基盤がそのまま渡してくれる。ファイルは読みに行く必要があり、パスをどこかで決めなければならず、そのパスをまた設定で持つことになる。

ただし環境変数は平坦である。`DB_POOL_MAX=10` は書けるが、接続先ごとに違うプール上限は `DB_PRIMARY_POOL_MAX` `DB_REPLICA_POOL_MAX` と増やしていくしかない。ファイルなら階層で書ける。階層が要る設定と、平坦で足りる設定は、同じサービスの中に混ざっている。

先に読むべきなのは、起動に必要な最小限で、それは接続先とポートと秘密情報くらいである。これは環境変数に置く。残りはファイルに置いて、ファイルのパスだけを環境変数で渡す。では、既定値はどこに書くのか。

## 既定値

既定値はコードに書く。これで問いの半分には答えたことになる。

設定ファイルの雛形に既定値を書く流儀もあるが、雛形は配布された時点でコードから離れ、コード側の既定値が変わっても雛形は古いままになる。既定値をコードに置けば、設定ファイルには「変えたい値」だけが残る。設定ファイルを読んだ人が、どこを変えたのかを一目で見られる。

秘密情報の既定値は書かない。書いた既定値はリポジトリに残り、残った値は本番で使われる。ここは空で落ちるほうがよい。

## 上書きの順序

残りの半分は、上書きの順序である。コードの既定値、ファイル、環境変数、コマンドライン引数の順に、後のものが前のものを上書きする。

順序の根拠は、変更の粒度にある。コードの既定値は全員に効き、ファイルは環境ごと、環境変数はプロセスごと、引数は一回の起動ごとに効く。粒度の細かいものが粗いものに勝つ。この順序を逆にすると、一回だけ試したい値のためにファイルを書き換えることになる。

順序を決めても、決めた順序を読み手が知らなければ同じことである。起動時に、どのキーがどこから来たかを一度だけログに出す。そうしなかったことを悔やんだ回数は、順序を間違えた回数より多い。
