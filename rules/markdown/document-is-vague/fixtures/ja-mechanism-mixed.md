# セッションストアを Redis に切り替えた理由

アプリケーションを水平にスケールさせようとすると、いずれセッション状態をどこに置くかという問題に向き合うことになる。プロセス内にセッションを持たせていると、あるユーザーのリクエストは常に同じサーバーに届く必要があり、これが選択肢を狭め、運用を複雑にしてしまう。共有ストアへの移行は、後々になって多くの面で報われる類の変更だ。

仕組み自体はシンプルで、セッションオブジェクトをワーカープロセスのメモリに持つ代わりに、シリアライズして Redis にセッション ID から導出したキーで書き込み、セッションの想定寿命に合わせて有効期限を設定する。各リクエストはロードバランサーがどのワーカーにでも振り分けられるようになる。ワーカーは自分のメモリではなく Redis からセッションを読むため、前回のリクエストをどのプロセスが処理したかに依存しなくなるからだ。

こうしたアーキテクチャには多くのメリットがある。システムはより堅牢になり、より柔軟になり、より把握しやすくなる。この種の変更を行ったチームの多くは、スケーリングにまつわる様々な頭痛の種がまるごと消えてなくなることに気づき、将来的により良いインフラ選択への道が開けることになる。

さらに、Redis の有効期限機構をそのまま活用できるのも利点だ。古くなったセッションを見つけて削除する専用のスイープジョブを走らせる代わりに、書き込み時に設定した TTL にその仕事を任せることができ、期限切れのキーはただ存在しなくなるだけで済む。

全体として、これはアーキテクチャにとって良い変更で、結果には満足している。この種のインフラへの投資は、システムが成長するにつれてずっと報われ続けるものだ。
