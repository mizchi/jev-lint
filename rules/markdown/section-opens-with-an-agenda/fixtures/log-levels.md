# WARN は誰のためか

ログレベルの選び方に正解はない、とよく言われる。正解はある。ただし、それは書く側ではなく、読む側の都合で決まる。

## WARN

WARN は、今すぐ人が動く必要はないが、放置すると ERROR に育つ事象に付ける。設定ファイルの非推奨キー、リトライで救えた失敗、期限が近い証明書。どれも今日の動作には影響しない。

ここで、書く側は「念のため」を WARN にしがちである。どうか、ここから先は監視する側の目線で読んでほしい。監視する側は WARN の件数をグラフにしている。「念のため」の WARN が一日に千件出るサービスでは、証明書の期限が近いという一件は、千件の中に埋まる。

つまり WARN の価値は、その件数の少なさで担保されている。念のための WARN を足すたびに、既存の WARN の価値が薄まる。アラートは鳴らないのだから、問題はないに違いない。

## ERROR

ところが、ERROR の側でも同じことが起きていた。リトライで救えた失敗を ERROR にしていたサービスでは、ERROR が一日に数百件出る。アラートは件数の閾値で鳴るように直され、閾値は数百のすこし上に置かれた。本当の障害で ERROR が数百件を超えるまで、誰も気づかない。

ここまでの話を「WARN を全部消せ」という主張と読まれると、それは違う。消すべきなのは、読む側が動かない WARN である。読む側が動く WARN は、件数が少なければ少ないほど価値がある。

ERROR は、人が今すぐ動く事象に付ける。動かないなら ERROR ではない。動くべきなのに動けないほど件数が多いなら、それはログレベルの問題ではなく、障害の問題である。

## INFO

以下では、INFO の出力量について説明する。

INFO は、あとから経緯を追うためのものである。リクエストの開始と終了、外部呼び出しの相手と所要時間、状態遷移。読む側は障害のあとにこれを読むので、件数は多くて構わない。代わりに、一件の中に追跡できる識別子が要る。識別子のない INFO は、多ければ多いほど読めなくなる。

識別子をどう付けるかは、次の節で見る。

## 識別子

リクエストの入口で一つ発行し、そのリクエストに関わるすべての INFO に載せる。外部を呼ぶときはヘッダに載せて渡し、相手のログにも同じ識別子が残るようにする。非同期のジョブに引き継ぐときは、ジョブのペイロードに載せる。

載せ忘れた箇所は、障害のときに「ここから先が追えない」という形で見つかる。見つかるたびに載せる。三回目の障害のころには、載せ忘れはほとんど残っていない。
