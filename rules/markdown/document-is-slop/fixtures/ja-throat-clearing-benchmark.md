# キャッシュ層を挟んで API のレイテンシを半分にした話

Web API の応答速度は、サービスを使うユーザー体験に直結する要素の一つで、多くのチームが一度は真剣に向き合うことになるテーマだと思う。リクエストが増えるにつれてバックエンドの負荷も増え、どこかのタイミングでキャッシュを検討する場面は誰にでも訪れるはずだ。

キャッシュの入れ方に唯一の正解はなく、サービスの特性によって適切な構成は変わってくる。それでも、自分たちが何を変えて何が起きたかを数字とともに書き残しておく方が、後から見返すときに役立つと考え、この記事にまとめることにした。

## 変更前の状態

商品詳細 API は毎回 PostgreSQL に対して JOIN を含むクエリを発行しており、p50 で 80ms、p99 で 420ms かかっていた。リクエスト数はピーク時で 900 req/s。

## やったこと

1. **Redis に商品詳細を JSON でキャッシュ**。TTL は 30 秒。キャッシュキーは `product:{id}:{version}` で、商品が更新されるたびに version をインクリメントすることで、TTL を待たずに古いキャッシュを無効化できるようにした
2. **キャッシュミス時の同時リクエストをまとめる**。同じキーへのミスが同時に複数来た場合、最初の1件だけ DB に問い合わせ、残りはその結果を待つようにした（singleflight パターン）。ピーク時に同じ商品が一斉にキャッシュ切れするケースで DB への同時クエリ数が最大 140 件から 1 件に減った
3. **ヒット率を計測できるようにした**。Redis の `INFO` から `keyspace_hits` / `keyspace_misses` を Prometheus に出し、ダッシュボードに乗せた

## 結果

| | 変更前 | 変更後 |
| --- | --- | --- |
| p50 | 80ms | 6ms |
| p99 | 420ms | 45ms |
| DB への QPS | 900 | 65 |
| キャッシュヒット率 | - | 94% |

計測は変更後 1 週間分のアクセスログから集計した。

## 残った課題

ヒット率 94% の内訳を見ると、ミスの大半は新規追加された商品への初回アクセスで、これは TTL やキー設計を変えても避けられない。ここをさらに削るなら、商品追加時に先読みでキャッシュを温めておく必要があり、まだ手を付けていない。
